Important current architecture:

- `step_reference(...)` is still the authoritative full reference simulator step.
- `ReferenceBackend` wraps `step_reference(...)`.
- `step_reference(...)` composes:
  1. `step_lane_change_reference(...)`
  2. `step_longitudinal_reference(...)`
  3. restores lane-change flags from the lane-change phase.
- Longitudinal phase has internal array-level kernels.
- Lane-change phase has internal array-level kernels:
  - target-lane neighbor lookup;
  - eligibility;
  - proposal collection;
  - stochastic conflict resolution;
  - applying accepted lane changes.
- There is no optimized full-step backend yet.
- There is no Numba longitudinal kernel.
- There is no Numba lane-change kernel.
- Optional Numba indexing kernels exist, but Numba is optional and must not be required.
- Occupancy and gaps remain head-cell-only.
- Vehicle length remains metadata only for indexing/gap/lane-change logic.
- Controlled RL action semantics are not implemented yet.

Goal
====

Add benchmark tooling that measures full-step and phase-level costs after the longitudinal and lane-change kernel splits.

This task is benchmark-only.

The purpose is to produce enough evidence to decide the next optimization task based on measured bottlenecks, not guesses.

The benchmark must answer:

1. How expensive is one full `step_reference(...)` call?
2. How expensive is a multi-step reference rollout?
3. How much time is spent in:
   - occupancy construction;
   - lane ordering;
   - neighbor computation;
   - lane-change proposal collection;
   - lane-change conflict resolution;
   - applying accepted lane changes;
   - longitudinal phase;
   - validation / final occupancy checks where relevant;
   - object/state copying and orchestration overhead where possible.
4. How do costs change with:
   - number of lanes;
   - road length;
   - density;
   - number of rollout steps;
   - lane-change probability.
5. Which next implementation task is justified:
   - optimize indexing;
   - add Numba lane-change kernel;
   - add Numba longitudinal kernel;
   - design an optimized full-step backend;
   - defer optimization because current costs are acceptable.

# Timing methodology

Use only standard-library timing tools, preferably:

```python
time.perf_counter_ns()
```

Recommended methodology:

1. Generate the initial state deterministically per case/seed.
2. Run warmup iterations.
3. Run repeated benchmark iterations.
4. For each repeat, start from the same initial state and same RNG seed to keep repeats comparable.
5. Disable garbage collection inside the timed block if useful, but restore it afterward.
6. Report per-step metrics, not just total time.
7. Report median and mean across repeats.
8. Report min/max or q05/q95 if easy, but do not add dependencies for statistics.

Important:

* The benchmark should avoid changing simulator behavior.
* Phase-level benchmarking may reproduce the public step composition internally, but only inside the benchmark script.
* Any helper that reproduces the step phases must be benchmark-local.
* Do not move benchmark-only phase decomposition into public production API.

# Recommendation rules

Implement simple recommendation logic in the benchmark script/report.

Suggested rules:

* If indexing phases dominate, recommend improving indexing / neighbor computation before lane-change-specific optimization.
* If `lane_change_collect_proposals` dominates, recommend a dedicated Numba lane-change proposal/conflict kernel task.
* If `longitudinal_phase` dominates, recommend a Numba longitudinal kernel task.
* If `validation_and_final_checks` dominates but only in debug/reference mode, recommend separating benchmark/debug validation from production optimized backend design.
* If no single phase dominates, recommend an optimized full-step backend design task only after confirming orchestration/state-copy overhead.
* If measured smoke data is too small or noisy, explicitly say that standard benchmark must be run before choosing an optimization.

Do not overstate the results. The report must say these are local-environment benchmark results.
